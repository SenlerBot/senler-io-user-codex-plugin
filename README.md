# Senler.io User Codex plugin

Плагин подключает Codex к пользовательскому MCP-серверу Senler.io. Native OAuth предоставляет доступ к проектам и возможностям, доступным авторизованному пользователю Senler.io.

## Установка

Добавьте публичный marketplace:

```bash
codex plugin marketplace add https://github.com/SenlerBot/senler-io-user-codex-plugin.git
```

Установите плагин:

```bash
codex plugin add senler-io-user@senler-user
```

Проверьте установку:

```bash
codex plugin list --marketplace senler-user --available --json
```

У `senler-io-user@senler-user` должны быть `installed: true` и `enabled: true`.
Наличие marketplace без установленного плагина не загружает его инструменты и навыки.

Откройте новый чат Codex и запустите настройку плагина или попросите:

> Подключи Senler.io User и покажи доступные мне проекты. Пока ничего не изменяй.

Навык первого подключения проверит инструменты и выполнит чтение списка проектов.
При запросе авторизации пройдите OAuth в интерфейсе MCP-клиента, затем выберите
нужный проект. Пустой список проектов сам по себе не означает ошибку авторизации.
Доступ к списку также не доказывает наличие прав на изменение всех объектов.

## Если подключение не работает

| Симптом | Что проверить |
| --- | --- |
| Плагин есть в каталоге, инструментов нет | Установлен и включён ли плагин; после установки откройте новый чат или обновите клиент. |
| Требуется вход или истекла авторизация | Откройте настройки подключения Senler.io User в MCP-клиенте и пройдите подключение заново. Токены в чат передавать не нужно. |
| Не находится нужный метод | Попросите проверить метод через `diagnose_access`, если этот инструмент доступен. Причиной могут быть права или версия каталога. |
| Не хватает OAuth-разрешений | Переподключитесь с новым согласием на нужные права. Обновление старого токена не добавляет разрешений. |
| Нет доступа к конкретному проекту | Проверьте выбранный аккаунт, проект и текущие права участника. |
| Сервер не отвечает или возникает сетевая ошибка | Проверьте доступность сервера; повторный вход не устраняет сетевой сбой. |

Названия разделов настроек подключения зависят от клиента и его версии.

## Когда использовать

- чтобы увидеть доступные пользователю проекты;
- чтобы работать с данными и настройками разных проектов;
- чтобы управлять каналами, агентами, диалогами, лидами, приложениями и другими доступными сущностями;
- когда проектный плагин с доступом только к одному выбранному проекту слишком ограничен.

Для изолированного доступа только к одному выбранному проекту используйте отдельный плагин [Senler.io Project](https://github.com/SenlerBot/senler-io-codex-plugin).

Плагин не запрашивает токены в чате и не использует `OPENAI_API_KEY`. Авторизацией управляет MCP-клиент по стандартному OAuth.

## Обновление

```bash
codex plugin marketplace upgrade senler-user
codex plugin add senler-io-user@senler-user
```

После обновления откройте новую задачу Codex.

## Состав

- `.agents/plugins/marketplace.json` — публичный каталог;
- `plugins/senler-io-user/.codex-plugin/plugin.json` — manifest плагина;
- `plugins/senler-io-user/.mcp.json` — подключение к hosted MCP server;
- `plugins/senler-io-user/skills/senler-io-user/SKILL.md` — правила безопасной работы с Senler.io;
- `plugins/senler-io-user/skills/senler-io-user-setup/SKILL.md` — первый запуск и диагностика подключения;
- `scripts/validate-plugin.mjs` — проверка структуры пакета без подключения к Senler.io;
- `CHANGELOG.md` и `LICENSE` — история версий и лицензия MIT.

## Проверка изменений

Для проверки нужен Node.js 24; установка npm-зависимостей не требуется:

```bash
npm run check
```

Команда проверяет JSON, имена и пути, наличие навыков и ресурсов, onboarding,
согласованность OAuth-адресов, версии и типичные признаки попавших в пакет секретов.
Регрессионные проверки выполняются на временных копиях пакета. Эта проверка
не заменяет ревью секретов и реальное прохождение OAuth.
В workspace Aisenler команда автоматически использует общий heavy-task gate;
в отдельном клоне и GitHub Actions она работает самостоятельно.

Перед выпуском проверьте в Codex установку/обновление, новый чат, OAuth и чтение
доступных проектов. Для проверок записи используйте отдельно согласованный
тестовый проект. Не считайте проверку каталога подтверждением успешного входа.

## Выпуск версии

Обновите одинаково `version` в `package.json` и манифесте, добавьте запись в
`CHANGELOG.md` и выполните проверки. Версии обозначаются как `0.1.1`, `0.1.2` и т. д.
После коммита проверенных изменений создайте тег `v<version>` на этом коммите.
Публикация ветки и тега — отдельный шаг выпуска; проверка пакета сама их не отправляет.
GitHub Actions проверяет также совпадение тега с версией манифеста.

## Поддержка инструкций

Плагин задаёт рабочие правила Codex и первый запуск. MCP-сервер владеет актуальными
методами, схемами и протокольными инструкциями. При изменении общих правил сверяйте
их со skill, чтобы не появлялись противоречащие требования.
Инструкцию конкретного агента переносите только после проверки её контекста:
роль, интерфейс сайта, внутренние инструменты, идентификаторы и доступы конкретного
проекта не должны попадать в публичный универсальный плагин.

Для общей правки проверьте конкретный сценарий, выделите правило, применимое ко
всем клиентам MCP, и согласуйте его с серверной инструкцией. Настройки Codex и
первое подключение остаются в плагине; кнопки виджета, подсветка страницы и учёт
воронки конкретного помощника — в его инструкции. Не копируйте тексты целиком и
не синхронизируйте их автоматически из изменяемого production-агента.
